MiniVectorDB 本地实现

运行环境：Python 3.12；本地测试使用系统 python3；NumPy 2.0.1 用于分块向量数学运算，不承担存储或索引实现。无 NumPy 时核心可回退到纯 Python。
启动 SQL 入口：python3 -m minivectordb.server --data /data
示例：python3 -m minivectordb.server --data /tmp/minivectordb-example < examples/basic.sql
测试：python3 -m unittest discover -s tests -v
性能诊断：python3 scripts/benchmark_local.py --rows 1000 --queries 100
容器构建：docker build -t minivectordb .
容器运行：docker run --rm -i -v minivectordb-data:/data minivectordb

当前 SQL 输入按分号分隔，支持多行、字符串内分号、双单引号转义。
本地输出为 LOCAL_SQL_READY，其后每个操作输出 JSON；查询依次输出列名、逐行数据和完成标识。
这是本地适配格式，尚未对接正式 mysqltest 驱动，不应当宣称通过正式准入。
SQL 错误返回 ok=false，不静默接受未实现的语句。完整执行前检查尾部语法。
关闭输入流正常退出并回滚未提交事务。SIGKILL 后再次启动复用数据目录。

持久化与恢复
每张表的数据写入不可变二进制分段：长度头、UTF-8标量元数据、列名和连续float32向量。保留旧JSON行快照的读取兼容，写入/重建后使用新格式。主键为定长二进制有序分段，按区间排除不可能冲突的段，最多32段后合并。
普通插入追加分段，达到128段时合并；更新删除流式产生新一代文件；提交先 fsync 文件，再原子替换 manifest，最后 fsync 数据目录。
未提交数据文件不在已提交 manifest 中；恢复清理不可见版本，无需全库读入内存。
显式事务通过独立 catalog 视图实现读己之写；每条修改语句成功后才替换该表引用。
提交落盘失败后进程停止接收工作，避免不确定提交被错误回收。
恢复可重复执行；单进程独占目录，不支持多客户端或多个进程同时打开。

索引与查询
自实现平面向量索引，二进制保存主键、记录偏移和 float32 向量。
exact 查询分块扫描索引，NumPy计算距离和过滤。标量列缓存预算4MiB，按不可变索引文件及块定位；预算不足时逐行过滤，不积累整个块的大字符串。更新和回滚按文件可见性清理缓存。TopK先分区保留距离边界上的候选，再按距离及主键排序，最终候选回表读取。索引更新仍采用整表重建。
先过滤再 TopK，平局主键升序，返回欧氏距离；距离以双精度累加存储值差平方。
普通排序使用有界分块及最多32路归并。TopK 使用 O(K) 堆。

已知差距
正式协议、错误码、模式参数尚未接入，不能直接正式提测。
支持 --mode exact 或 ann；ann 当前回退到精确扫描，Recall 为精确结果，不宣称实现近似剪枝。
普通插入不重写表，但索引维护、更新删除与分段合并仍会重写表，存在写放大。
SQL 解析当前将单条语句及其 INSERT 值放入内存，大事务可写磁盘，但超大单语句仍需限额验证。
主键检查使用有界外部排序和磁盘有序分段，不在每次提交时重写全部主键。无序插入范围高度重叠时，查重仍需读取相交分段。
尚未完成官方大于内存数据集、资源硬限制及全部语法兼容性验证。
Docker 镜像已实际构建，基础镜像锁定摘要；初版24项回归在禁网、2 CPU、128MiB 容器内通过；优化版新增格式兼容、缓存、分段及精度边界验证，容器强杀与退出回滚验证通过。

完整本地评测交付入口
依赖：Linux x86_64、Python 3、Docker daemon；驱动端执行 python3 -m pip install -r requirements.txt。
一条命令：make evaluate
该命令构建镜像，在禁网容器中运行回归和独立SQL用例，执行三轮10000行/128维/1000次查询负载，并执行64MiB超内存数据测试。
快速检查：make evaluate-quick（1000行、20次查询、1轮，不执行超内存压力测试）。
原生快速功能检查：python3 scripts/evaluate.py。
所有输出进入 artifacts/<时间戳>/report.json、各阶段 .log 和每个进程的 transcript.jsonl/stderr.log。
返回码0代表所选择的本地检查全部通过，非0代表失败；失败数据保留用于重现。成功数据默认清理，可加 --keep-data 保留。
通过 --output 指定一个尚不存在的输出目录；评测不会覆盖旧报告。
当前完整命令使用128MiB作为功能/性能内存限制，资源测试单独使用64MiB，不冒充官方冻结配置。
详细接口见 evaluation/PROTOCOL.txt。

可编辑SQL用例
在 tests/sql/ 新建同名 .test 和 .result，评测入口会自动发现。
.test 支持多行SQL，语句最后一行以分号结束；支持 --error、--restart、--kill、--sorted_result 独立指令行。
.result 是每条SQL对应的 {"error":布尔值,"rows":结果数组} 的JSON数组；重启指令不产生结果项。
--sorted_result 将下一条查询的行按JSON文本排序，预期文件需保持相同顺序，用于未指定ORDER BY的集合比较。
这是一套明确的本地用例格式，不声称与组织方 mysqltest 完全兼容。

第一轮性能优化
SQL以完整向量字面量分词，借助标准JSON解析器批量解析数值；语句边界用正则扫描完整引用区间，减少逐字符Python解释开销。SQL的非JSON数值语法和注释仍有校验及兼容路径。
二进制行、分段主键和过滤缓存均保持原提交持久化协议；本轮对照使用相同2 CPU、128MiB容器、种子与10000行/128维/1000查询负载，结果见 validation/optimization/。
旧格式兼容为单向升级：新版可读取旧JSON行快照，新写入采用二进制行和分段主键。回退旧程序时应使用独立的数据目录，旧程序不能读取新版快照。

第二轮性能优化
数值向量优先使用整段字符类分词，复杂注释/非JSON数值仍走原兼容解析。主键暂存扫描只读取标量字段，跳过向量载荷；不超过4096个主键的批次在有界内存中排序，更大批次仍使用外部排序。
精确查询使用只读内存映射按2048条分块读取索引；映射不将全索引载入Python堆，实际页缓存仍计入cgroup。距离通过单次float64减法分配减少临时数组；结果投影复用同一查询的TopK距离，不重新计算。
旧提交4575c6cf的实测镜像作为第二轮基线，保持同一配置、种子和精确校验。原有持久化成功确认时机与fsync步骤未放宽。
第二轮交错实测结果见 validation/optimization-round2/summary.json。复现交错测量：python3 scripts/compare_images.py --baseline 已构建的旧镜像 --candidate 新镜像 --output 尚不存在的结果目录。本次归档的完整功能/资源记录在 validation/optimization-round2/gates/ 下，测试数量已增加到34。

第三轮性能优化
自实现 native/topk.c 提供精确L2与TopK数学内核，通过ctypes访问只读索引块，减少NumPy临时数组及解释器调度。编译禁用浮点乘加收缩，CPU运行时检测AVX2，不支持时使用标量路径；不使用现成向量索引库。
Docker采用多阶段构建，在构建阶段以锁定版本GCC12编译，运行镜像只复制共享库，不携带编译器。默认要求原生库成功加载，不静默把加载故障当成原生优化成绩；MINIVECTOR_NATIVE=0可显式使用原NumPy路径。
本地开发运行 make native 或 python3 scripts/build_native.py 编译；make test 会先编译再运行测试。make native-check 运行AddressSanitizer/UBSan独立原生测试，需要本机GCC。仅运行 make evaluate 不需要宿主机编译器，Docker内会从源码构建。
共享库为生成物，不纳入源码提交；没有本地库时原生Python入口仍可回退。完整Docker镜像内同时包含标量与AVX2实现。

第四轮性能优化
普通追加批次使用MVDBROW2布局：记录区后附有序主键区，文件头保存记录区结束偏移。记录与主键一起flush/fsync后，再同步并原子发布manifest，最后同步/data目录；普通批次的独立同步调用从4次变为3次，不提前确认提交。
读记录时按明确的记录区边界停止，不将主键尾部作为记录解析。主键有序分段支持旧字符串文件引用和新描述符混合读取。建向量索引或重写表数据时将尾部主键分离，避免仅为保留主键而长期保留旧向量副本。
旧JSON行、MVDBROW1和旧主键分段保持读取兼容；旧程序不支持MVDBROW2及新描述符，回退须使用独立数据目录。
float32类型校验和舍入增加CPython原生接口，严格区分bool、int和float，拒绝非有限值及转换溢出；使用当前解释器头文件编译，Docker固定为Python3.12。本地更换解释器后须执行make native重新构建，生成物不提交。
make native-check现在同时检查TopK内核和CPython编码接口。后者使用malloc对象分配并关闭全解释器LSan汇总；部分列表的引用释放另由tracemalloc回归验证。

第五轮性能优化
原生精确扫描尽可能在一次调用中完成整个只读索引的TopK，减少分块候选在Python中的归并。过滤位图按不可变索引版本和完整WHERE条件缓存，每次查询仍计算当前向量的精确距离。
保留映射对象的总文件长度预算8MiB，过滤位图预算2MiB，标量列缓存预算4MiB；大索引按需映射而不转换为全量Python堆数组。过滤记录数超过262144时使用分块路径。写入、回滚和索引重建按文件版本清理缓存，关闭数据库释放缓存引用。
当已累积的非负平方距离严格大于当前第K名时，原生计算提前停止该候选。等于边界的候选继续计算，以保留距离并列时的主键顺序。投影不需要向量时，回表只解码标量字段并复用已计算的距离。
新增完整向量资源测试：140000条128维记录建索引并重启，在64MiB cgroup下执行过滤和无过滤精确查询，数据与索引总量大于内存预算。
资源测试区分内核控制器完成状态与严格峰值状态，原始memory.peak及OOM事件均保留；评分使用实际峰值，不裁剪。默认检查memory.max配置、禁用swap、无OOM事件和结果正确性；加 --strict-peak 可同时要求原始峰值不超过memory.max。make evaluate MINIVECTOR_EVAL_FLAGS=--strict-peak 可启用。
Linux明确说明memory.max在特定情况下允许短时越界，因此原来的单独峰值断言可能因内核计量边界失败。本轮归档保留首次失败和诊断信息；本轮最终完整验收仍使用--strict-peak，两个资源测试同时满足严格峰值条件。参考 https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files 。
