MiniVectorDB 开发与优化说明
更新日期：2026-11-09

一、交付内容

在 2026-competition-round2 分支实现了单机向量数据库，包括数据库源码、
Dockerfile、运行说明、本地评测工具和 agent/conversation.json。

已实现：
• SQL：建表，多行 INSERT，SELECT 投影，UPDATE、DELETE，比较条件与 AND，
  ORDER BY、LIMIT；BIGINT 主键、Unicode VARCHAR、固定维度 float32 VECTOR。
• 检索：L2_DISTANCE、精确 TopK、过滤后 TopK、距离并列按主键排序，
  CREATE VECTOR INDEX，以及插入、更新、删除后的索引维护。
• 事务：自动提交、BEGIN / COMMIT / ROLLBACK、事务内读到自身修改、
  失败语句原子性、提交持久化、强制终止与重复恢复。
• 运行：stdin/stdout 连续 SQL 交互，数据统一写入 /data，Docker 从源码构建。

二、实现结构

存储采用不可变二进制数据段和 manifest。数据段保存标量、float32 向量与
有序主键目录；追加写入避免整表重写，定期合并控制段数量。提交先同步
数据文件，再同步并原子替换 manifest，最后同步目录。恢复依据已发布的
manifest 确定可见数据，并清理孤立文件。

向量索引自行实现，保存主键、记录位置及连续向量数据。查询使用只读 mmap、
过滤位图和 C TopK 内核；内核按 CPU 能力选择 AVX2 或标量路径，采用双精度
累加。大数据处理使用分块扫描、受限缓存和外部排序。

主要代码位置：
• minivectordb/core.py：存储、事务、恢复、索引与查询。
• minivectordb/sql.py：SQL 解析、执行与投影规划。
• native/topk.c：距离计算、TopK、float32 输入转换。
• evaluation/、scripts/、tests/：评测驱动、性能比较、正确性与资源验证。

三、已完成的优化

测量负载：10,000 条记录、128 维、1,000 次 TopK 查询、K=10，半数查询
带等值过滤；容器配置为 2 CPU、128 MiB。下列各轮分别比较对应的新旧镜像，
采用三轮中位数，耗时单位为秒。

轮次  核心改动                                  写入           查询
1     二进制行、追加段、主键有序段、批量解析    13.80→3.39     34.05→6.15
2     mmap、减少数组复制、复用距离、主键扫描    3.48→2.46      6.36→4.17
3     自研 C / AVX2 精确 TopK 内核              写入逻辑不变   4.77→2.35
4     行与主键目录合并落盘、原生 float32 转换  2.28→1.86      2.10→2.10

第五轮已在本地实现：
• 整个索引交给原生内核扫描，减少分块调用与 Python 合并开销。
• mmap、标量列、过滤位图采用有容量上限的缓存，并随索引版本失效。
• 利用距离累加下界提前结束落后候选的计算，保持精确排序与主键并列规则。
• 推迟读取向量；仅查询主键和距离时直接由索引返回，省去基础记录读取。

第五轮当前完整三轮测量：批量写入 1.81 秒，1,000 次查询 1.33 秒；
有过滤、无过滤两组 Recall@10 均为 1.0。

六、第六轮：直接访问过滤候选

过滤命中记录不超过全表的 1/8 时，将缓存位图转换为有序 uint32 位置列表。
原生 TopK 直接读取这些位置，省去对其余记录的位图检查；其余过滤继续
使用位图。缓存保持 2 MiB 容量上限，索引版本切换时按原有规则失效。
检索仍采用精确距离计算。无过滤和候选列表分别编译，消除扫描循环中的
路径选择分支。尝试过的 AVX2 多累加链因未显示收益而撤回。

短内核对比：10,000 条、128 维、K=10，每轮 300 次查询，交错三轮中位数。
• 命中 1%：5.059 ms → 3.321 ms，速度为原来的 1.52 倍。
• 命中 10%：12.098 ms → 12.179 ms，基本持平。
• 无过滤：82.190 ms → 83.516 ms，基本持平。
以上是原生内核耗时；全流程最近一次完整测量仍为第五轮的 1.33 秒。

针对性验证覆盖候选列表、空结果、不同维度、K 边界、并列距离与事务回滚，
并对原生路径执行 ASan / UBSan 检查。对比脚本为 scripts/compare_native.py，
原始测量记录为 validation/optimization-round6/kernel-comparison.json。
第六轮改动随本次规则审核一同交付。

七、第七轮：SQL 计划复用与结果输出

为带向量字面量的 SELECT 增加 128 KiB 查询计划缓存。缓存语句结构和
参数位置，新请求重新绑定向量、检查维度与数值，并读取当前表及事务状态。
同一距离表达式的投影和排序复用一次绑定结果。缓存保留语法结构，不保存
查询答案；大语句超出容量时直接解析执行。

小结果合并为一次写出与刷新，大结果按 64 Ki 字符分块输出；JSON 编码器
复用，避免逐行创建编码器和包装字典。Top10 的输出刷新由 12 次降至 1 次。

本地 SQL 进程短对比：10,000 条、128 维、600 次查询（200 条不同 SQL
重复三遍）、半数带过滤，交错三轮中位数 0.320 秒 → 0.304 秒，耗时减少
约 5%。校验全部主键、排序和距离。测量记录保存在
validation/optimization-round7/transport-comparison.json。

仅合并输出的第一版未显示收益，记录在 output-first-attempt.json；加入
编码器复用后的单独对比记录在 output-encoder-comparison.json。
针对性检查覆盖缓存容量、新参数验证、延迟消费结果、事务状态、分块输出
和错误结果。第七轮改动随本次规则审核一同交付。

八、第八轮：压缩向量筛选，保持精确 TopK

为不超过 8 MiB、32～4096 维的向量索引生成 .q8 压缩文件，每个分量占
1 字节。查询先计算整数距离，根据编码重建误差界排除确定不能进入 TopK
的候选，再用原始 float32 向量计算最终距离。并列规则保持主键升序。
候选少于 512、K 较大或查询超出编码范围时使用原精确扫描。

压缩文件写入 /data，落盘后随 manifest 一起提交；更新、回滚、重启和
孤立文件清理均按索引版本处理。映射与原索引共用 8 MiB 缓存预算。
10,000 条、128 维增加 1,280,036 字节持久化文件。

短内核对比中，无过滤提速 2.40 倍，10% 候选过滤提速 1.28 倍。
本地完整 SQL 对比使用两个常驻进程、每 20 条交错执行、三轮中位数：
600 次查询从 0.495 秒降至 0.424 秒，耗时减少约 14%，主键、排序和距离
全部通过独立参考结果校验。工作负载与第七轮相同。

4 项针对性检查覆盖极大值、次正规数、奇数维度、空结果、并列距离、
索引更新、重启、回滚及缓存容量；原生路径通过 ASan / UBSan 检查。
记录位于 validation/optimization-round8/，其中保留分时启动对比及最终
交错批次对比。第八轮改动随本次规则审核一同交付。
