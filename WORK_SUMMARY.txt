MiniVectorDB 开发与优化说明
更新日期：2026-11-09

一、交付内容

在 2026-competition-round2 分支实现了单机向量数据库，包括数据库源码、
Dockerfile、运行说明、本地评测工具和 agent/conversation.json。

已实现：
• SQL：建表，多行 INSERT，SELECT 投影，UPDATE、DELETE，比较条件与 AND，
  ORDER BY、LIMIT；BIGINT 主键、Unicode VARCHAR、固定维度 float32 VECTOR。
• 检索：L2_DISTANCE、精确 TopK、过滤后 TopK、距离并列按主键排序，
  CREATE VECTOR INDEX，以及插入、更新、删除后的索引维护。
• 事务：自动提交、BEGIN / COMMIT / ROLLBACK、事务内读到自身修改、
  失败语句原子性、提交持久化、强制终止与重复恢复。
• 运行：stdin/stdout 连续 SQL 交互，数据统一写入 /data，Docker 从源码构建。

二、实现结构

存储采用不可变二进制数据段和 manifest。数据段保存标量、float32 向量与
有序主键目录；追加写入避免整表重写，定期合并控制段数量。提交先同步
数据文件，再同步并原子替换 manifest，最后同步目录。恢复依据已发布的
manifest 确定可见数据，并清理孤立文件。

向量索引自行实现，保存主键、记录位置及连续向量数据。查询使用只读 mmap、
过滤位图和 C TopK 内核；内核按 CPU 能力选择 AVX2 或标量路径，采用双精度
累加。大数据处理使用分块扫描、受限缓存和外部排序。

主要代码位置：
• minivectordb/core.py：存储、事务、恢复、索引与查询。
• minivectordb/sql.py：SQL 解析、执行与投影规划。
• native/topk.c：距离计算、TopK、float32 输入转换。
• evaluation/、scripts/、tests/：评测驱动、性能比较、正确性与资源验证。

三、已完成的优化

测量负载：10,000 条记录、128 维、1,000 次 TopK 查询、K=10，半数查询
带等值过滤；容器配置为 2 CPU、128 MiB。下列各轮分别比较对应的新旧镜像，
采用三轮中位数，耗时单位为秒。

轮次  核心改动                                  写入           查询
1     二进制行、追加段、主键有序段、批量解析    13.80→3.39     34.05→6.15
2     mmap、减少数组复制、复用距离、主键扫描    3.48→2.46      6.36→4.17
3     自研 C / AVX2 精确 TopK 内核              写入逻辑不变   4.77→2.35
4     行与主键目录合并落盘、原生 float32 转换  2.28→1.86      2.10→2.10

第五轮已在本地实现：
• 整个索引交给原生内核扫描，减少分块调用与 Python 合并开销。
• mmap、标量列、过滤位图采用有容量上限的缓存，并随索引版本失效。
• 利用距离累加下界提前结束落后候选的计算，保持精确排序与主键并列规则。
• 推迟读取向量；仅查询主键和距离时直接由索引返回，省去基础记录读取。

第五轮当前完整三轮测量：批量写入 1.81 秒，1,000 次查询 1.33 秒；
有过滤、无过滤两组 Recall@10 均为 1.0。

四、已有验证结果

当前本地版本通过 50 项回归、5 项评测工具检查和 11 个 SQL 用例，覆盖
事务、索引维护、异常退出、恢复及缓存失效。原生内核完成独立参考结果
对照及 AddressSanitizer / UndefinedBehaviorSanitizer 检查。

资源验证在 64 MiB 容器内完成：
• 80,000 条记录的标量存储负载。
• 140,000 条、128 维向量的数据与索引负载，文件合计 154,338,155 字节；
  完成重启、过滤与无过滤检索，严格峰值检查通过，OOM 事件为 0。

前四轮比较记录位于 validation/optimization*；第五轮完整验证记录位于
/tmp/minivector-round5-release-gates/report.json。
